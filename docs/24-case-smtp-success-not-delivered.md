# 案例05：SMTP 发送成功但用户未收到邮件 — 投递链路认知

> **故障等级**: P2（用户未收到关键通知邮件）  
> **发生时间**: 2026-10（服务器论文通过邮件排查）  
> **状态**: 【曾经发生】【已修复】【已验证】

---

## A. 故障现象

管理端论文审批通过后，邮件中心显示发送状态为"已提交至邮件服务器"（SUCCESS），但投稿者反馈未收到邮件。

## B. 排查过程

1. **检查邮件中心记录**：mail_send_record 中 status=SUCCESS(1)，SMTP 返回 250 OK
2. **检查收件人地址**：地址正确无误
3. **检查垃圾邮件箱**：用户确认不在垃圾邮件中
4. **检查退信记录**：mail_bounce_record 中无该收件人的退信
5. **检查 IMAP 收件箱**：BounceEmailJob 轮询的发件箱 IMAP，未发现退信
6. **最终定位**：SMTP 250 OK 只代表**邮件服务器接受**，不代表**最终投递到对方邮箱**

## C. 根因分析

**邮件投递链路多环节，SMTP 成功只是第一步**。

```
发件方SMTP → 250 OK → 发件方服务器投递队列
  → DNS查询MX记录 → 收件方SMTP → 收件方过滤(垃圾邮件/灰名单)
  → 投递到邮箱 / 退信 / 静默丢弃
```

可能原因：
1. 收件方邮件服务器静默丢弃（未返回退信）
2. 收件方灰名单延迟（首次接收延迟，重试后才投递）
3. 邮件被过滤到用户不可见的隔离区
4. DNS 解析延迟导致投递超时

## D. 修复方案

**短期**：人工确认用户邮箱后手动重发。

**长期（系统级）**：
1. **IMAP 退信检测**：BounceEmailJob 定时轮询收件箱，捕获退信 → 更新状态为 BOUNCE_DETECTED
2. **9 态状态机**：SUCCESS 不再是终态，退信检测后才确认最终投递状态
3. **重试机制**：退信后可重试（临时退信）或加黑名单（永久退信）
4. **AGENTS.md 规范**：明确写入"SMTP 发送成功≠邮件最终送达"

## E. 验证方式

1. 模拟退信场景：向不存在邮箱发送 → IMAP 检测到退信 → 状态更新为 BOUNCE_DETECTED
2. 正常投递：向有效邮箱发送 → 用户确认收到
3. 重试流程：退信后手动重试 → 状态流转 RETRYING → RETRY_SUCCESS

## F. 影响范围

- 所有依赖邮件通知的业务（注册成功/论文通过/密码重置）
- 修复前：无法感知投递失败，用户收不到邮件也无从知晓
- 修复后：退信可检测、可重试、可追踪

## G. 经验教训

1. **SMTP 250 ≠ 投递成功**：这是邮件系统最核心的认知，必须区分"服务器接受"和"最终投递"
2. **退信检测是必须的**：没有退信检测的邮件系统是"盲发"
3. **任务表模式的价值**：先落库再发送，退信后可追溯原始记录并重试
4. **邮件不是可靠通信**：关键业务不能只依赖邮件，应有页面状态查询作为补充（如"我的注册"页面）
